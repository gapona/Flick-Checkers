# Задача: единая UI-система + навигационный каркас (Flick Checkers)

Контекст: игра `Flick Checkers` на `Phaser_Core` — щелчковая физическая игра по мотивам советского
«Чапаева» (см. `GAME-PLAN.md`). Доска — **вид сверху, квадрат**, изометрия отменена (§2
плана). Проект отпочкован от `Casual Draughts`, поэтому UI унаследован точечным: каждая сцена
рисует свои кнопки, размеры разъезжаются, у оверлеев нет затемнения, safe-area не учитывается.
Нужно перейти на общие компоненты, после чего экраны собираются из них.

**Работать чанками в этом порядке.** Каждый следующий опирается на предыдущий; не начинать
следующий, пока предыдущий не проходит свой DoD. **Не трогать `src/sim/`** — солвер, шаг
симуляции, детерминизм и `runToRest()` вне этой задачи целиком. Задача про UI и про то, как
UI читает состояние симуляции, а не про саму физику.

---

## Инварианты, которые нельзя нарушать

Из `Phaser_Core/CLAUDE.md`, проверять на каждом чанке:

- Позиционирование **только** в `layout()`, никогда в `create()`.
- Весь HUD добавляется в `uiCamera` и исключается из `cameras.main` через `.ignore()`;
  мировые объекты — наоборот. `Camera.ignore()` не действует задним числом — всё, что
  создаётся в рантайме (летящие шашки, частицы удара, индикатор силы), идёт через
  `addWorldObject`/`addHudObject`.
- `setMask()` под WebGL — тихий no-op. Клип только через `scrollableCameraRegion()`.
- `setInteractive()` на объекте нулевого размера не создаёт `.input`. Повторный
  `setInteractive()` не пересчитывает hit-area — мутировать `input.hitArea` напрямую в
  `layout()`.
- `Container` имеет захардкоженные `originX/Y = 0.5` со смещением точки хит-теста — не
  вешать интерактивность на контейнеры, только на явные `Rectangle`/`Zone`.
- Ввод только через `bindAction()`, никогда сырой `.on('pointerdown')`. Единственное
  исключение — доска, см. чанк 8.
- Новая overlay-сцена обязана быть добавлена в `OVERLAY_SCENES` в `lifecycle.ts`.
- Все строки через `t()`, **обе локали в одном коммите** — иначе билд красный по
  компайл-тайм паритету словарей.
- `MIN_TOUCH_TARGET = 44` — для всего UI без исключений. Доска не в счёт: у неё своё
  правило в чанке 8, и это другой механизм попадания, а не послабление порога.
- Поля инстанса не переинициализируются при рестарте сцены — состояние UI заводить в
  `create()`, а не в объявлении поля.

## Чанк 1 — `src/ui/button.ts`: единая фабрика кнопок

**Проблема.** Кнопки подгоняют ширину под длину лейбла, поэтому в одном стеке они разной
ширины. С испанской локалью разброс станет сильнее.

**Решение — фиксированные токены размера, лейбл подгоняется под кнопку, а не наоборот.**

```ts
export type ButtonSize = 'primary' | 'secondary' | 'compact' | 'icon'
export type ButtonVariant = 'gold' | 'plum' | 'ghost'

// базовые размеры в дизайн-единицах, умножаются на uiScale()
const SIZES = {
  primary:   { w: 280, h: 72 },
  secondary: { w: 280, h: 64 },
  compact:   { w: 168, h: 56 },
  icon:      { w: 64,  h: 64 },
}
```

Правила:

- Ширина **не зависит** от лейбла. Длинный текст ужимается через `fitScale()` с полом
  `0.7`; если не влезает и на `0.7` — обрезка с многоточием, но кнопка не растёт.
- Все кнопки внутри одного стека/строки обязаны иметь одинаковый размер. Смешивать токены
  в одной группе запрещено.
- Хит-область — отдельный `Rectangle`, не контейнер, минимум 44×44 после `uiScale()`.

**Визуал:**

- вертикальный градиент от светлого верха к насыщенному низу;
- светлый rim 2 px по верхней кромке;
- тёмный контур 3 px по всему периметру;
- **нижняя «толщина» 6 px** более тёмным тоном — кнопка выглядит физическим объектом;
- нажатие: сдвиг вниз на 3 px + толщина схлопывается до 0, отпускание возвращает с
  `Back.easeOut`;
- disabled: насыщенность вниз, толщина остаётся, лейбл на 45 % альфы;
- `gold` — главное действие, ровно одно на экран. `plum` — всё остальное. `ghost` — только
  отмена/закрытие.

Лейбл: тяжёлый скруглённый гротеск, тёмная обводка, мягкая тень. Обводка обязана быть темнее
самой тёмной точки градиента самой кнопки, иначе она спорит с фоном.

`neonButton()` из ядра не используется в игре вообще. Не удалять его (ядро общее), просто
не вызывать.

**DoD:** визуальная страница-стенд со всеми размерами × вариантами × состояниями (normal /
hover / pressed / disabled) на 390×844 и 1280×720. Все кнопки одного токена попиксельно
одинаковы.

## Чанк 2 — `src/ui/chrome.ts`: safe-area и верхняя панель

```ts
export interface Insets { top: number; right: number; bottom: number; left: number }
export function screenInsets(scene: Phaser.Scene): Insets
```

- База — `SAFE_AREA_TOP_MARGIN_PX = 24` из ядра.
- В портрете `top += 30` (требование сертификации Playables).
- **Нижний инсет: `bottom = 20` в портрете, `0` в ландшафте** — под home indicator iOS.
  Нижняя навигация из чанка 3 без этого будет перекрыта.
- В ландшафте `left`/`right` по 16 — вырез сбоку.

`TopBar` — компонент, обязательный на **каждой** сцене, собирается один раз:

| Слот | Содержимое | Условие |
|---|---|---|
| крайний левый | кнопка «Назад», токен `icon` | скрыта на корневом `MainMenu` |
| левый | бейдж монет | всегда |
| центр | индикатор раунда `2 / 5` | только в `Game` |
| крайний правый | шестерёнка настроек, токен `icon` | всегда |

Высота полосы 72 + `insets.top`. Кнопка «Назад» ведёт на предыдущую сцену по стеку
навигации, а не жёстко на `MainMenu` — завести `navStack` в реестре сцен, иначе из Shop,
открытого из Game, вернёт не туда.

`bindAction('back')` должен ловить и аппаратную кнопку «назад» Android, и `Escape`.
**Внутри `Game` «назад» во время летящей симуляции не выходит из матча**, а поднимает
подтверждение выхода — иначе случайный тап выбрасывает из середины раунда.

**DoD:** на 390×844 с эмулированным `env(safe-area-inset-top) = 47` ни один элемент
`TopBar` не заходит в зону чёлки; кнопка «Назад» отсутствует ровно на `MainMenu`.

## Чанк 3 — `src/ui/navBar.ts`: нижняя навигация

Три вкладки: **Home / Shop / Режимы**. Паттерн взять из `navTabs` в `patches-daily`.

- Высота 88 + `insets.bottom`.
- Каждая вкладка: иконка 32 px над лейблом, вся вкладка — равная треть ширины, хит-область
  на всю треть.
- Активная: золотая, приподнята на 4 px, иконка на 10 % крупнее. Неактивные: сливовые,
  альфа 0.75.
- Переключение вкладок — без анимации перехода сцен (`sceneTransition` только для входа в
  Game и выхода из него), иначе навигация ощущается вязкой.

**В сцене `Game` навигация скрыта, и здесь это жёстче, чем было в шашках.** Доска —
квадрат и упирается в меньшую сторону вьюпорта; в портрете 88 px снизу отобрали бы у неё
около 11 % стороны, то есть напрямую уменьшили бы каждую шашку и точность прицела. В Game
работает только кнопка «Назад» в `TopBar`.

**Следствие для `MainMenu`:** остаются `Continue` (`gold`) и `New match` (`plum`), обе
токеном `primary`. Режимы — в навигации, настройки — под шестерёнкой.

**DoD:** переход между тремя вкладками на всех трёх вьюпортах, активное состояние
читается однозначно, навигация не появляется в Game.

## Чанк 4 — Оверлеи: затемнение и блокировка ввода

- Полноэкранный скрим `0x0a0612` с альфой `0.72`, фейд 120 мс.
- Скрим — интерактивный `Rectangle`, поглощающий все клики (иначе кнопки под панелью
  остаются кликабельными).
- Тап по скриму вне панели закрывает оверлей. **Исключение — панель результата (чанк 10):
  она закрывается только кнопкой.**
- Панель въезжает с `Back.easeOut` от 0.92 масштаба, уезжает линейно за 100 мс.
- Каждый оверлей зарегистрирован в `OVERLAY_SCENES` в `lifecycle.ts` — иначе сломается
  пауза/возобновление на сворачивании вкладки.

**DoD:** ни на одном оверлее не читается контент нижней сцены; клик сквозь панель
невозможен; `Escape` и аппаратная «назад» закрывают верхний оверлей, а не выходят из игры.

## Чанк 5 — `src/ui/slider.ts` + переработка настроек

Заменить `Sound: ON` / `Music: ON` на два регулятора громкости.

- Трек 240×12, скруглённый, тёмная подложка + золотая заливка до позиции ручки.
- Ручка 32 px, круглая, с толщиной и контуром как у кнопок. **Хит-область ручки раздута до
  44×44** — сама ручка меньше порога.
- Работает и перетаскивание ручки, и тап по треку (мгновенный переход в точку).
- Слева от трека иконка-кнопка mute (`icon`): выключает в 0, повторное нажатие возвращает
  прежнее значение. Иконка меняется по уровню: 0 / <50 % / ≥50 %.
- Шаг 5 %, значение показывается числом справа.
- Оба слайдера одной ширины, выровнены по левому краю с лейблами `SFX` и `Music`.
- Живой отклик: при отпускании SFX-ручки проиграть **звук удара шашки о шашку** на
  выставленной громкости. Это главный звук игры, по нему и надо выставлять уровень.

**Это меняет схему сейва — сделать аккуратно.**

```ts
// было
settings: { sound: boolean; music: boolean }
// стало
settings: { sfx: number; music: number }   // 0..1
```

Миграция в `migrate.ts`: `true → 1`, `false → 0`. Выбрать один вариант — бампнуть версию
схемы или держать булевы вычисляемыми от чисел — и записать решение в `GAME-PLAN.md` §8.

**DoD:** громкость переживает reload; крайние значения 0 и 1 работают; сейв со старой
булевой схемой открывается без потери настроек.

## Чанк 6 — Экран `Режимы`

Заменяет экран выбора набора правил из шашек. Содержимое другое, лэйаут тот же.

- Контентная колонка: `min(720, vw - 32)`, центрирована. То же ограничение применить ко
  **всем** экранам меню — растяжка во всю ширину на десктопе выглядит сломанной везде.
- Карточки режимов: `Классика`, `С бортами`, `Дуэль на время`, `Ежедневка`. Зазор 12 px,
  внутренние поля 16 px, скруглённые.
- На карточке: название, одна строка про то, чем режим отличается, и **иконка-схема
  доски** — с бортами по периметру или без. Разница «шашка вылетает / шашка отскакивает»
  словами не читается, схемой читается сразу.
- Список — через `scrollableCameraRegion()`, не `setMask()`.
- Выбранная карточка ровно одна: золотая рамка + золотая галочка справа + подложка на тон
  светлее. Невыбранная — сливовая рамка без свечения.

Сложность — сегментированный контрол `Easy / Medium / Hard` под списком, три сегмента
равной ширины, над ним лейбл `Difficulty`. Под контролом одна строка пояснения: сложность
здесь — это точность бота, а не другие правила для него (§6 плана). Игрок должен понимать,
что Hard не жульничает.

**DoD:** на 390×844 список скроллится, выбранный режим однозначно опознаётся, ничего не
выходит за контентную колонку на 1920×945.

## Чанк 8 — Доска: попадание по шашке и прицел

Ядро игры, и здесь правила расходятся с остальным UI. Решение принять явно и записать.

**Отдельных интерактивных объектов на шашках нет.** При тайле 48 px (8×8 на вьюпорте
390 px) диаметр шашки — около 38 px, то есть ниже `MIN_TOUCH_TARGET`. Раздуть хит-области
до 44 нельзя: в стартовой расстановке шашки стоят вплотную, раздутые области перекроются,
и тап между двумя шашками достанется произвольной.

Вместо этого — **один невидимый интерактивный `Rectangle` на весь мировой слой**, и по
`pointerdown` выбирается **ближайшая своя живая шашка** к точке в мировых координатах,
с порогом в 1.2 радиуса. Тот же приём, что уже использовался в шашках для клеток; он
переживает любой зум и ресайз бесплатно.

Прицел:

- Драг **от шашки назад**: направление = от пальца к шашке, сила = длина драга с потолком.
- Индикатор силы — не число, а сама линия прицела: длина и толщина растут до потолка, на
  потолке она меняет цвет. Игрок не должен переводить взгляд на HUD во время прицела.
- **Траектория рисуется только до первой преграды**, дальше нет. Полная траектория решает
  выстрел за игрока.
- **Отмена**: палец вернулся ближе чем на 0.5 радиуса к центру шашки — сила 0, выстрела
  нет. Показывать явно (линия гаснет), иначе игрок не поверит, что отмена сработала.
- Палец перекрывает ту самую шашку, по которой целится. Линию и дугу силы рисовать так,
  чтобы они читались **за пределами** пальца — от шашки в сторону выстрела, а не под ним.

**Состояние «летит»:** пока `runToRest()` не завершился, ввод по доске заблокирован, и это
должно быть видно — не спиннером, а тем, что подсветка активной стороны гаснет. Спиннер на
двухсекундном ожидании выглядит как загрузка, а это не загрузка.

**DoD:** на 390×844 сто тапов по стартовой расстановке выбирают ближайшую к пальцу шашку в
100 случаях из 100; отмена прицела работает; во время симуляции ни один тап по доске не
проходит.

## Чанк 9 — HUD сцены `Game`

- **Портрет:** доска по центру, `TopBar` сверху (монеты, раунд `2 / 5`, шестерёнка). Под
  доской узкая полоса: слева бейдж-капсула статуса (`Ваш ход` / `Думает…` с идл-анимацией),
  справа две кнопки расходников токеном `compact`, одинаковые по размеру.
- **Ландшафт:** боковые панели в мёртвом поле по сторонам квадратной доски. Слева статус и
  счётчик шашек, справа расходники.
- **Счётчик шашек — главный элемент HUD, а не украшение.** Две группы точек по числу живых
  шашек каждой стороны; выбитая гаснет анимацией в момент вылета. Это единственный
  индикатор того, кто выигрывает.
- Комбо за выстрел (§5 плана) — всплывающий текст **у места удара на доске**, не в HUD. Он
  живёт полторы секунды и не занимает постоянного места.
- Индикатор чьего хода — не только текст: подсветить рамку доски со стороны активного
  игрока. Во время симуляции подсветка гаснет (чанк 8).
- Дебажный оверлей убрать за `import.meta.env.DEV`, литерал зарегистрировать в
  `check-bundle.mjs`.

**DoD:** на 844×390 доска не меньше, чем без HUD (панели встают в мёртвое поле сбоку); на
390×844 всё влезает без скролла; счётчик шашек читается на расстоянии вытянутой руки.

## Чанк 10 — Панель результата

Отдельный чанк, потому что это экран, который игрок видит чаще всех остальных: раз в раунд,
то есть пять раз за матч.

**Разбор по скриншоту** (панель `Shields down` — из другого прототипа, но ошибки типовые и
переедут сюда, если не назвать их явно):

1. **Скрима нет.** Вокруг панели читается сцена: фон, деревья, корабль. Игровой фон
   конкурирует с итогом. Чинится чанком 4 — панель результата обязана его использовать.
2. **Кнопка вне панели.** `Again` висит под рамкой и выглядит элементом другого слоя.
   Кнопки — внутри панели, в её нижней зоне, с отступом 24 от нижней кромки.
3. **Панель почти пустая.** Контент занимает верхнюю треть, ниже примерно 40 % пустоты.
   Высота панели должна считаться от контента (`padding + контент + padding`), а не быть
   константой. Пустая панель читается как «здесь что-то не загрузилось».
4. **Нет иерархии в цифрах.** `Score 9365`, `Best 9365`, `Waves 5 of 5` — три строки одного
   кегля и веса. Главное число обязано быть крупным (в 2.5–3 раза), остальное — подписями
   под ним.
5. **Лейбл и значение в одной центрированной строке.** При переходе числа с четырёх знаков
   на пять вся строка съезжает. Нужна двухколоночная сетка: лейблы по правому краю левой
   колонки, значения по левому краю правой, обе колонки фиксированной ширины.
6. **`Score` и `Best` совпали — это новый рекорд, и он никак не отмечен.** Рекорд — момент,
   а не строка в таблице: бейдж `Новый рекорд`, отдельный звук, досчёт числа вверх.
7. **Один выход.** Кроме `Again` идти некуда — игрок заперт в цикле. Нужны минимум два
   действия.
8. **Победа и поражение выглядят одинаково.** Отличается только заголовок; ни цвет рамки,
   ни акцент кнопки не меняются.
9. **Числа появляются мгновенно.** Досчёт вверх — самый дешёвый приём, превращающий
   результат в событие; в `patches-daily` он уже написан.

**Каким он должен быть в Чапаеве.** Две панели, общая вёрстка, разное содержимое.

**Результат раунда** (после каждого рода войск):

| Зона | Содержимое |
|---|---|
| Заголовок | `Раунд выигран` / `Раунд проигран` + название рода войск |
| Герой | Число оставшихся своих шашек, крупно. Это и есть итог раунда |
| Строки | `Выбито шашек`, `Лучшее комбо`, `Выстрелов`, `Монет` — двухколоночная сетка |
| Бейджи | `Всухую`, `Новый рекорд комбо` — только когда заслужены |
| Действия | `Дальше` (`gold`, `primary`) и `Выйти в меню` (`ghost`, `secondary`) |

**Результат матча** (после пяти раундов): счёт раундов `3 : 2` крупно, полоса из пяти
отметок по раундам, итоговый счёт, действия `Ещё раз` (`gold`) и `В меню` (`ghost`). Если
результат превысил `bestScore` — бейдж рекорда и `sendScore()`.

Правила для обеих:

- Ровно одна золотая кнопка. Вторая — `ghost`.
- Панель не растёт шире 280 на телефоне; на десктопе ограничена контентной колонкой.
- Числа досчитываются вверх за 400 мс, бейджи появляются после досчёта, звук рекорда — в
  момент появления бейджа, а не открытия панели.
- Панель результата **не закрывается тапом по скриму** — только кнопкой. Случайный тап не
  должен пропускать итог раунда.
- Победа: рамка золотая, акцент тёплый. Поражение: рамка сливовая, акцент холодный,
  заголовок без восклицания. Различие обязано читаться раньше, чем прочитан заголовок.
- Награда за раунд начисляется в момент завершения симуляции, а не по кнопке — иначе выход
  через панель теряет монеты.

**DoD:** оба варианта панели на 390×844 / 844×390 / 1920×945 в состояниях победа /
поражение / победа с рекордом; высота панели меняется вместе с числом строк; сквозь скрим
не читается доска; тап мимо панели ничего не закрывает.

## Чанк 11 — Контраст доски и различимость сторон

**Клетки — линейка, а не картинка.** В Чапаеве клетки не несут правил, они нужны только
для того, чтобы глаз оценивал расстояния и силу удара. Поэтому контраст между светлой и
тёмной клеткой около **2:1**, и самая светлая точка доски темнее блика на шашке. Если
доска светлее фигур, она «выступает» вперёд и мешает целиться.

**Край доски — самая важная линия на экране.** Именно вылет за него решает игру. Край
должен читаться как обрыв: рамка с внутренней тенью, клетки последнего ряда чуть темнее.
Проверить отдельно: видно ли на 390×844, что шашка стоит в полуклетке от края.

**Стороны — золотая и сливовая.** Прогнать обязательный тест: скриншот доски в градациях
серого. Если стороны сливаются — это блокер, и различие доводится **формой** (гранёный
ободок против гладкого) в дополнение к цвету. При виде сверху форма ободка читается лучше,
чем читалась в изометрии, так что это дешевле, чем кажется.

**Тень шашки — отдельный спрайт со смещением** (§2 плана). Проверить, что в полёте она
остаётся под шашкой, но смещение фиксировано относительно доски, а не относительно спрайта.

**DoD:** скриншоты стартовой расстановки и середины раунда на 390×844 в цвете и в
градациях серого; в обоих режимах стороны различимы, шашки доминируют над доской, край
доски читается однозначно.
